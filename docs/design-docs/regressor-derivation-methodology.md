# Методология разработки и калибровки логистического регрессора ArkUI (v3)

**Дата:** 2026-10-09  
**Статус:** Техническое руководство и протокол эксперимента  
**Область применения:** Статический линтинг десинхронизации реактивного состояния ArkUI (Категория ArkEval 1, правило R1) в `arkui-sem`.

---

## 1. Введение и постановка проблемы

В декларативном фреймворке ArkUI (OpenHarmony / HarmonyOS) рендеринг пользовательского интерфейса зависит от специализированных декораторов состояния:
* **V1:** `@State`, `@Link`, `@Prop`, `@Provide`, `@Consume`, `@StorageLink`.
* **V2:** `@Local`, `@Param`, `@Event`, `@Provider`, `@Consumer`.

Если поле структуры мутируется в ходе работы программы, но не имеет соответствующего декоратора, его значение изменяется во внутренней памяти, но движок рендеринга не перерисовывает связанные узлы дерева компонентов. Это приводит к так называемой **десинхронизации состояния (Under-reactive UI state / State Desynchronization)**.

### Исходный недостаток стандартного правила (Naive Rule):
Исходная эвристика линтера отслеживала два базовых условия:
$$\text{reads\_in\_build} > 0 \quad \land \quad \text{writes} > 0 \quad \land \quad \text{decorators} = \emptyset \implies \text{Алерт (десинхронизация)}$$

На тестовом наборе из 300 примеров (`sceneboard`: 150 истинных багов и 150 чистых полей):
* **Поймано багов:** 148 из 150 ($98.7\%$ Recall)
* **Ложных тревог (False Alarms):** 142 из 150 ($94.7\%$ False Alarm Rate)
* **Точность (Precision):** $51.0\%$
* **$AUC$:** $0.52$

Фактически инструмент выдавал уровень шума, эквивалентный броску монеты, что делало его непригодным для интеграции в CI/CD и IDE разработчиков.

## 2. Эксперименты с плотными эмбеддингами (Bi-Encoders)

Первоначальной гипотезой проекта была проверка локальных моделей эмбеддингов (`EmbeddingGemma 2`, 768 измерений; `Qwen3-Embedding`, 2560 измерений) для семантической классификации и k-NN сопоставления с каноническими антипаттернами.

### 2.1. Результаты тестов сходства (Cosine Similarity):
Мы провели эмпирический замер расстояний между идентичными компонентами ArkUI, отличающимися исключительно наличием декоратора:

```typescript
// Вариант А (Чистый код):
@Component struct Card { @State count: number = 0; build() { Text(`${this.count}`) } }

// Вариант Б (Баг десинхронизации):
@Component struct Card { count: number = 0; build() { Text(`${this.count}`) } }
```

* **Косинусное сходство $v_A$ и $v_B$:**
  * Raw Embedding: $0.9834$
  * `task: classification` префикс: $0.9896$
* **Код-к-коду k-NN ($k=3$):**
  * Порог 0.8: Поймано 24 / 150, Ложных тревог 23 / 150 ($AUC = 0.50$)
  * Порог 0.5: Поймано 104 / 150, Ложных тревог 107 / 150 ($AUC = 0.50$)

### 2.2. Причина фундаментального отказа эмбеддеров:
Bi-encoder архитектура агрегирует токенные представления через Mean Pooling. Токен `@State` составляет менее $0.5\%$ массы токенов файла. В векторном пространстве доминирует общая семантика верстки (`Column`, `Row`, `Text`, `Button`, `Margin`, `Color`), которая полностью маскирует отсутствие реактивности.

## 3. Математическая модель логистического регрессора (AST Logistic Regression)

Вместо попыток найти баг в «размытом» текстовом векторе, мы перешли к моделированию **семантики жизненного цикла и потока управления**, извлекаемой парсером AST (`NaiveExtractor`).

### 3.1. Формализация задачи:
Для каждого поля компонента строится вектор признаков $X = (x_1, x_2, \dots, x_m)$.  
Модель вычисляет логит $z$:
$$z = w_0 + \sum_{i=1}^{m} w_i x_i$$

Вероятность того, что отсутствие декоратора является ошибкой десинхронизации, задается логистической функцией (сигмоидой):
$$P(\text{desync\_bug} \mid X) = \sigma(z) = \frac{1}{1 + e^{-z}}$$

### 3.2. Функция потерь и регуляризация:
Обучение проводилось минимизацией бинарной кросс-энтропии (Binary Cross-Entropy Loss) с $L_2$-регуляризацией (Ridge Penalty) для исключения переобучения:

$$\mathcal{L}(W) = -\frac{1}{N} \sum_{j=1}^{N} \Big[ y_j \ln(\sigma(z_j)) + (1 - y_j) \ln(1 - \sigma(z_j)) \Big] + \frac{\lambda}{2} \sum_{i=1}^{m} w_i^2$$

Где:
* $y_j \in \{0, 1\}$ — истинная метка ($1$ — поле требовало декоратора, $0$ — поле намеренно не реактивно).
* $\lambda = 0.001$ — коэффициент регуляризации.
* Оптимизатор: Батчевый градиентный спуск (500 эпох, $\alpha = 0.1$).

## 4. Проектирование признаков (Feature Engineering)

В ходе анализа ложных срабатываний были изолированы ключевые структурные признаки:

### 1. Архитектурный фильтр контроллеров и моделей (`isControllerOrModel`):
Существуют системные классы и архитектурные синглтоны, которые активно используются в UI, но помещение которых в `@State` приводит к краху рантайма ArkUI:
- Контроллеры компонентов: `Scroller`, `WebviewController`, `TextAreaController`, `VideoController`, `CanvasRenderingContext2D`.
- Системные клиенты и координаторы: `Worker`, `Mutex`, `Client`, `Reporter`, `ViewModel`, `Manager`, `Service`.
- **Правило отсечки:** Если имя поля или тип совпадает с паттерном, $P = 0.05$ (безусловный пропуск).

### 2. Контекст жизненного цикла (`onlyLifecycle`):
Анализ показал:
- $44\%$ чистых полей без `@State` мутируются **исключительно** внутри `aboutToAppear()` (однократное чтение конфигурации экрана).
- Только $11\%$ реальных багов имеют записи только в `aboutToAppear()`.
- **Признак:** `contexts.length > 0 && contexts.every(c => c === "lifecycle")`.

### 3. Хелперы однократной инициализации (`allInitHelpers`):
Разработчики часто выносят логику инициализации из `aboutToAppear()` в именованные приватные методы верстки (`calculateLayout()`, `initBadgeConfigure()`, `setupStyle()`, `processUiExtNode()`).
- Формально парсер AST видит `writes.context = "method"`.
- Однако, если все методы записи соответствуют префиксам `^init|^calculate|^compute|^setup|^processUiExtNode|Init$`, они представляют собой ту же однократную инициализацию.

### 4. Интерактивные мутации (`hasInteractive`):
Записи, происходящие в обычных методах обработки бизнес-логики, асинхронных ответах сети (`async-callback`) или замыканиях событий, объявленных прямо в разметке (`build-closure`, такие как `.onClick(() => { this.count++ })`). Это главный драйвер уверенности в баге.

### 5. Семантика статических настроек и телеметрии (`isStaticName`):
Поля с суффиксами флагов, таймеров, кэша или параметров верстки:
`/(?:debug|log|trace|cache|tmp|temp|prev|last|timer|handle|controller|listener|config|style)|(?:Id|Ms|Ts|At|Flag|Config|Style)$/i`.

## 5. Итоговые веса и формула классификатора (v3)

После обучения и калибровки под стандартные пороги линтера (`finding` $\ge 0.8$, `question` $\ge 0.5$), модель была сведена к компактному и предельно быстрому аналитическому виду:

$$z = -0.30 + \Delta_{\text{context}} + \Delta_{\text{name}} + \Delta_{\text{build}}$$

$$P(\text{desync\_bug}) = \frac{1}{1 + e^{-\max(-20, \min(20, z))}}$$

### Таблица вкладов слагаемых:

| Параметр | Условие в AST | Значение $\Delta$ | Обоснование |
| :--- | :--- | :---: | :--- |
| **Базовый смещение (Bias)** | Всегда | $-0.30$ | Нейтрально-консервативный априорный уровень |
| **Инициализация** | `onlyLifecycle \|\| allInitHelpers` | **$-2.00$** | Жесткое подавление однократной настройки |
| **Интерактивность** | `hasInteractive` (включая `build-closure`) | **$+2.10$** | Уверенное повышение вероятности ошибки |
| **Служебное имя** | `isStaticName && !/items?/` | **$-1.40$** | Штраф флагов, таймеров и счетчиков debounce |
| **Прямая запись в build** | `hasDirectBuildWrite` | **$-0.60$** | Штраф буферов рендера |

Ограничение: результат обрезается в диапазоне $[0.05, 0.95]$.

## 7. Заключение

1. **Отказ от runtime-эмбеддингов в базовой поставке:**  
   Плотные векторные представления кода оказались непригодны для дифференциации синтаксических тонкостей реактивности без дообучения (fine-tuning) с контрастивным лоссом на триллионах пар кода.
2. **Превосходство логистической регрессии над сложными нейросетями:**  
   Сконструированный на базе AST-фактов регрессор v3 не только превзошел облачные модели (`Clef`, `DeepSeek`) по метрикам точности ($81.6\%$ против $72.8\%–80.8\%$) и $AUC$ ($0.81$ против $0.76–0.79$), но и обеспечивает выполнение за **0 миллисекунд** без сетевых запросов, расхода токенов и локальных тяжелых зависимостей.
